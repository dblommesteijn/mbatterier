# menulets

The menu bar app and its Control Center control, the only Swift in this repo.
What they do and how to install them: [main README](../README.md#menu-bar-app).

```
MBatterier/
├── Info.plist            LSUIElement, so no Dock icon
├── MBatterier.entitlements   the App Group shared with the control
└── Sources/
    ├── main.swift          bootstrap
    ├── AppDelegate.swift   status item, menu, refresh triggers, actions
    ├── ControlCenterFrame.swift  whether Control Center is open, and its panel's corner
    ├── ZoomOpen.swift      the menu growing out of the tapped tile, and collapsing or fading on close
    ├── Status.swift        mirror of `status --json` and `energy --json` + StatusReader (execs the CLI)
    ├── BarText.swift       menu and bar wording (pure)
    ├── BarGlyphs.swift     bar image: High Power chevrons + battery
    ├── BatteryIcon.swift   the battery, fill colour per mode
    ├── TimerIcon.swift     the boost stopwatch
    ├── EnergyBadge.swift   Energy Mode badges, header icons (quit, 👁, ∞)
    └── MenuRow.swift       custom menu rows, hover buttons and tips
MBatteryControl/          the Control Center controls, a widget extension
├── Info.plist            built into MBatterier.app/Contents/PlugIns
├── MBatteryControl.entitlements   sandbox + the App Group
├── Assets.xcassets       the battery symbols, generated by tools/symbols.py (git-ignored)
├── glyphs.swift          the system font's digits for those symbols (make symbols)
├── WidgetKitSPI.swiftinterface   WidgetKit's preferred control size, missing from the SDK
└── Sources/
    └── BatteryControl.swift  the three controls, their value, their tap (OpenMenuIntent)
Shared/
└── ControlSnapshot.swift what the menulet hands the control, in both targets
launchd/                  per-user LaunchAgent, starts it at login
```

```sh
make TEAM=<team ID> menulet | install-menulet; make uninstall-menulet   # from the repo root
make reload-control    # after an install, if the control still runs old code; then open Edit Controls
```

## The menu from Control Center

Tapping the control opens the menu, which behaves like the details of Apple's
own modules:

- **Opening:** it grows out of the tapped tile, over where Control Center was,
  in Control Center's dark look.
- **Closing with the Control Center button:** the menu stays where it is until
  Control Center's panel is back (it comes a moment after the click), then
  shrinks back into the tile as the panel fades in.
- **Closing any other way** (a click elsewhere, Escape, an item that leaves
  the menu): it fades out where it is, since there is no tile to go back to.
  After a click on another menu bar item it waits up to 0.8 s for Control
  Center first, then fades.

### How it is done

AppKit owns the menu's window and doesn't animate it, so `ZoomOpen.swift`
grows a stand-in: a borderless glass window (`ZoomWindow`) holding a picture of
the rows (`pictureOfOpenMenu`, pinned to the top at the target size by
`topAligned`, so a menu of another height keeps its margins). The real menu is
popped up over it. The code depends on these facts, all measured on macOS 27:

- **Growth** runs on a critically damped spring (`SpringFrame`, period
  `zoomResponse` 0.20 s) on the window's display link, not
  `NSAnimationContext`: a Bézier can't start from rest, and the ease-out it
  replaced jumped 40% in the first frame. Window frames are whole points, so
  the spring stops within 1 pt; closer in it only crept a point a frame.
- **Handover in** (`removeUnderMenu`): the shape sits a level *above* the menu
  (`popUpMenu + 1`). At the menu's first drawing (`MenuDrawSignal`) the menu
  window goes to alpha 0; two frames later the menu goes to alpha 1 and the
  shape to 0 together. Hiding the shape in the same commit as that drawing
  still left a frame of bare Control Center (6 taps in 10: the menu reaches
  the screen a frame late). Holding the shape over a visible menu blurred
  glass over glass, which came out darker, and fading it out was darker still,
  for longer. After the swap the shape stays up as a drawn, transparent
  window, so any later swap is just an alpha change (redrawing its glass took
  about 60 ms).
- **The picture** must match the menu pixel for pixel or the swap shows. Rows
  scale as a whole (`PictureView`), and labels in a vibrant appearance are
  drawn under the plain one (`plainAppearance`): offscreen there is no
  vibrancy blend, so the chevron came out dark grey.
- **A normal close fades** the menu window's alpha over 0.25 s on the main
  thread, and `menuDidClose` / `didEndTracking` only arrive after that.
  `watchMenuClosing` takes the first alpha strictly between 0 and 1 as the
  start (exactly 0 means the shape is standing in, below).
- **A click on another menu bar item** (the Control Center button) removes
  the menu in the click's frame, before any app hears of the click: a
  listen-only `CGEventTap` saw it 15 ms later (no permission needed), a global
  `NSEvent` monitor 40 ms later, and hooking `orderWindow:relativeTo:` on
  `NSPopupMenuWindow` never fired. So whenever the pointer is in the menu bar,
  where no click is meant for the menu, `watchMenuBar` has the shape stand in
  for the menu (menu alpha 0), and the tap (`watchClicks`) starts the
  collapse.
- **Control Center comes back late:** its panel appeared about 0.45 s after
  the click and faded in over about 0.15 s. After a close with the pointer in
  the menu bar, the shape waits for the panel (`waitForControlCenter`, up to
  0.8 s, `controlCenterIsOpen`) and only then shrinks into the tile;
  otherwise it fades in place (`fadeOut`, 0.25 s). It can't tell the Control
  Center button from other menu bar items, hence the timeout.
- **Per-frame drawing on the main thread freezes** during AppKit's fade,
  because the fade holds the main thread. Keep the shape's content
  GPU-scaled (an `NSImageView` inside `PictureView`).

Check any change here by recording the screen
(`screencapture -v -V <s> -R <rect>`, then extract frames with
`ffmpeg -fps_mode passthrough`). The problems were gaps of 1 to 3 frames that
no log shows.

## Rules

- **The CLI is the source of truth.** The app shows `mbatterier status --json`
  and acts through `mbatterier` commands. No `pmset`, no power logic in Swift.
  A new feature starts as a CLI field or command; `Status.swift` and
  `statusDoc` in `main.go` change together.
- **System APIs only as triggers.** The power-source notification and the
  file watches on `/Library/Preferences` and `/var/run` only prompt a re-read.
- **Don't observe the button's `effectiveAppearance`.** Setting the title or
  image changes it, so redrawing on it loops forever at full CPU. Redraw on
  the system theme notification and the regular refresh instead.
- **No background behind the item**, so the bar's translucency shows through.
- **Rows keep the menu open on click**, except ones that leave the app
  (Battery Settings…).
- **The control only reads the snapshot.** It is sandboxed and cannot run the
  CLI, so the menulet writes `ControlSnapshot` to the App Group on every change
  and reloads it. The control computes nothing.
- No Xcode project: `swiftc` lines in the Makefile, plus
  `appintentsmetadataprocessor` for the control's intent. Signed with your
  Apple Development certificate (`SIGN_ID`, `TEAM`), since the App Group needs a
  team; ad hoc is not enough.
- **The extension imports more WidgetKit than the SDK declares.** The Makefile
  builds it against the SDK's WidgetKit interface with
  `WidgetKitSPI.swiftinterface` appended: `preferredControlSize`, which the
  framework exports but the SDK's interface leaves out. It sets the size the
  Edit Controls gallery shows a control in. Keep that file to what the
  framework exports, or the extension won't launch.
